`supabase/migrations/0005_pin_ownership.sql`로 전도 대상자 등록 시 4자리 숫자 비밀번호를 입력받아 pgcrypto 해시로 저장하고, 수정/삭제/상태변경은 이 비밀번호를 다시 입력받아 SECURITY DEFINER RPC(`holywin_create_entry`/`holywin_update_entry`/`holywin_update_status`/`holywin_soft_delete_entry`)에서 해시 비교로 인증하는 방식으로 바꿨다. 기존 `owner_id`/`auth.uid()` 기반 RLS 정책은 건드리지 않고 그대로 남겨뒀다(방어선용, 실제로는 더 이상 클라이언트가 이 경로를 타지 않음).

**의도적으로 남겨둔 한계:** "내가 쓴 글" 필터 탭은 비밀번호와 무관하게 여전히 이 기기(브라우저)의 localStorage(`holywin_my_entry_ids`)만 본다 — 즉 비밀번호를 알아도 다른 PC에서 "내가 쓴 글" 탭에 자동으로 뜨지 않는다(전체 탭에서 직접 찾아 열면 수정/삭제는 비밀번호로 가능). 사용자가 이 구조를 이해하고 "이대로 두고 넘어가자"고 명시적으로 승인함(2026-09-30).

**다음 작업으로 확정된 것:** "제출자 이름으로 검색" 기능 추가. "내가 쓴 글" 탭(또는 그 옆)에 제출자 이름을 입력해 `from_name` 기준으로 필터링하는 UI를 추가하는 방향으로, 사용자가 명시적으로 이 방향을 선택했다(비밀번호를 "내 글 찾기" 용도로 서버에 질의하는 방식은 4자리 PIN이 브루트포스에 약해 일부러 배제함). 동명이인이면 다른 사람 글도 섞여 보일 수 있다는 트레이드오프는 이미 설명하고 승인받음.

**Why:** 사용자가 "다른 PC에서 봐도 같은 정보(내가 쓴 글)를 볼 수 있냐"고 질문해서, 비밀번호 기반 권한 모델과 "내가 쓴 글" 필터가 서로 다른 메커니즘이라는 걸 명확히 설명한 뒤 나온 결정.

**How to apply:** 이 기능을 다시 건드릴 때 이 결정 두 가지(현재 한계를 알고 있음 + 다음은 이름 검색)를 전제로 진행할 것. [[project-supabase-crud-migration]]의 소유권 모델 설명은 이제 이 비밀번호 방식으로 대체됐으므로 함께 갱신 필요.
