PWA 설치 유도 기능을 Plan Mode(Explore → Plan 에이전트 → 계획 파일 → ExitPlanMode 승인)로 설계하고, HTML/CSS/JS를 전부 구현한 뒤 code-reviewer 리뷰까지 돌렸다(1차 BLOCKED, 원인은 배너가 리스트 카드를 가리는 레이아웃 버그). 그런데 사용자는 그 버그를 고쳐달라고 하지 않고, 곧바로 "버튼을 QR 시트의 다른 버튼 옆으로 옮기고 배너는 통째로 삭제해달라"며 기능의 진입 방식 자체를 완전히 다른 구조로 바꿔달라고 요청했다. 이후에도 같은 세션에서 레이아웃을 두고 4~5차례 더(여백, 버튼 폭 분배 방식, 그림자, hover) 빠르게 뒤집었다 — 그중 일부는 직전에 적용한 CSS 기법(flex:none+nowrap)을 명시적으로 "없애달라"며 되돌리는 지시였다.

**Why:** [[user-screenshot-driven-iteration]]에 이미 기록된 "소규모 반복 조정 선호"가 개별 CSS 값 수준을 넘어, **이미 승인·구현된 기능/컴포넌트 구조 전체**에도 똑같이 적용된다는 걸 이번에 확인했다. Plan Mode를 거쳤다거나 code-reviewer가 APPROVED를 줬다는 사실이 사용자의 재설계 결정을 막는 근거가 되지 않는다 — 이 프로젝트는 실시간 렌더링 확인 수단이 스크린샷뿐이라([[feedback-ambiguous-visual-requests]]), 실제로 화면을 본 뒤에야 구조적 문제(공간 부족, 시각적 위계 등)가 드러나는 경우가 많다.

**How to apply:** 승인된 계획이나 통과된 리뷰를 "이미 정해진 것"으로 방어하지 말 것. 사용자가 기존 설계를 뒤집는 지시를 하면(예: "배너 없애고 다른 버튼 옆으로 옮겨줘") 왜 원래 설계가 나았는지 설득하려 들지 말고, 구조적으로 애매한 부분(예: 기존 배너의 문구/닫기 버튼은 어떻게 할지)만 짧게 확인 질문한 뒤 즉시 재설계에 들어간다. 재설계 후에도 다시 code-reviewer 승인 절차([[feedback-git-commit-pusher-unreliable]]와 별개로 이 저장소의 커밋 전 필수 게이트)는 동일하게 반복해야 한다 — 규모가 작아져도 생략하지 않는다.

**추가 사례(2026-09-23) — 훨씬 더 큰 규모, 그리고 "리뷰 통과"가 아니라 "리뷰 2회 통과"도 방어 근거가 안 됨:** 브라운 톤 7색 팔레트 + `--tone-1~5` 스케일 + 티켓 화면 3단 배경으로 색상 시스템 전체를 리브랜딩하고, code-reviewer 1차 BLOCKED → 수정 → 2차 APPROVED까지 받았다. 그런데 사용자는 승인된 그 상태를 보고 나서 "지금 보니깐 추구하는 컨셉과 좀 다른것 같아서"라며 색상 작업 전부를 원래 오렌지 라이트 테마로 롤백해달라고 요청했다 — 버그나 리뷰 지적이 아니라 순수하게 "실제로 보니 원하던 방향이 아니었다"는 이유였다. **리뷰 승인 2회를 받은 전면 리브랜딩도 예외가 아니다.**
같은 세션 안에서 더 작은 규모로도 반복됐다: 사용자가 참고 이미지(보딩패스 스크린샷, 특정 부분에 빨간 원 표시)까지 첨부하며 "여기랑 여기랑 시각적으로 분리되어 있잖아 붙여줘"라고 명확하게 요청 → 그 요청을 문자 그대로 정확히 구현(두 카드를 하나로 병합) → 사용자가 곧바로 "붙여줘의 이미지 그게 아니였어! 다시 이전 상태로"라며 직전 지시를 스스로 뒤집었다. 즉 **참고 이미지까지 첨부된, 실행 결과도 요청과 정확히 일치하는 지시조차 화면으로 직접 본 뒤 몇 초 만에 후회하고 되돌려달라고 할 수 있다.**
- **적용 시 태도:** "방금 정확히 요청하신 대로 했는데요"라고 방어하지 않는다. 되돌리는 지시가 오면 즉시 이전 CSS 값으로 되돌리고(git diff나 직전 대화의 값을 정확히 참조), 왜 그 결과가 기대와 달랐는지 캐묻지 않는다(사용자가 굳이 설명하면 참고만 한다).
- **부작용 주의:** 큰 롤백(색상 전체 등)을 할 때는 롤백 범위 밖의 독립적인 수정(예: 롤백된 배경 대비용으로 바꿨던 스탬프 색)이 롤백 후에도 남아 화면이 깨질 수 있다 — 되돌리는 작업도 일반 작업과 똑같이 스크린샷으로 직접 검증해야 한다.

**2026-09-25 추가 확인 — 되돌리는 대상이 "미학적 취향"이 아니라 "접근성/대비 안전 마진"이어도 똑같다.** `.ticket-hero`/`#screen-list`의 WCAG 대비를 맞추려고 code-reviewer 승인까지 받아 넣은 무채색 스크림 레이어를, 사용자가 "이거 모두 삭제해줘!"라고 명시적으로 요청했다. 삭제하면 사진의 밝은 영역과 흰 텍스트가 겹칠 때 대비가 기준 미달로 떨어질 수 있다는 트레이드오프를 먼저 설명했지만, 그 설명을 들은 뒤에도 사용자는 재차 "커밋/푸쉬 해줘"를 요청해 확정했다. **한 번 트레이드오프를 안내했다면 그걸로 충분하다 — 사용자가 위험을 알고도 진행을 재확인하면 더 이상 설득하거나 재차 경고하지 말고 그대로 실행한다.** (다만 code-reviewer 리뷰 자체는 "사용자가 원해서 대비가 나빠진 것"이라는 맥락을 리뷰 요청 프롬프트에 명시해서, 리뷰어가 대비 저하 자체를 이유로 BLOCKED하지 않도록 안내할 것 — 순수하게 "요청한 범위가 깨끗하게 반영됐는지"만 판단하게 한다.)
