한 세션 안에서 최소 세 번, 내가 직접 만들지 않은 변경이 working tree에 나타났다: (1) `assets/imgs/appIcon.png`가 1.2MB→133KB로 전체 픽셀이 바뀌어 있었던 것(나중에 사용자가 "로고를 바꿨다"고 확인) (2) `#screen-list`의 배경이 내가 넣은 다크 그라디언트 오버레이에서 단순 오렌지 틴트로 바뀌고 `.ticket-hero`의 스크림 레이어가 사라져 있었던 것(주석은 스크림을 설명하는 옛 문구가 그대로 남아 코드-주석 불일치가 생김) (3) 내가 만든 멀티사이즈 `appIcon.ico`(16/32/48/256px, 98KB)가 사용자의 다음 채팅 메시지가 오기 전 짧은 시간 안에 단일 16×16(463B)짜리로 바뀌어 있었던 것.

**Why:** 사용자는 코드/이미지 파일을 텍스트 에디터나 Finder, 외부 이미지 변환 도구로 직접 만지는 것을 편하게 여기고, 그 결과가 다음 채팅 턴이나 백그라운드 리뷰 에이전트 실행 사이에 조용히 working tree에 나타난다. 시스템이 명시적으로 "의도된 변경이니 되돌리지 말라"고 알려준 경우도 있었지만, 알려주지 않은 경우(예: appIcon.ico 단일 사이즈화)도 똑같은 패턴으로 발생했다.

**How to apply:** 예상치 못한 diff를 발견하면 먼저 `git diff --stat`/`git log -1 -- <path>`/파일 mtime으로 "언제, 얼마나" 바뀌었는지 확인하고, 그 시점이 내 마지막 도구 호출 이후라면 사용자의 직접 편집일 가능성을 우선 고려한다. 되돌리거나 "고치지" 말고, (a) 명백한 결함(예: 참조 경로가 깨짐, 이미지가 손상됨)이 있으면 그것만 짚어서 알리고, (b) 트레이드오프가 있는 변경(예: 화질 저하, 대비 저하)이면 간단히 안내만 하되 커밋을 막지는 않는다. [[feedback-post-approval-redesign-expected]]와 같은 축의 패턴 — "이미 정해진 것을 방어하지 않는다"가 파일 자체의 직접 편집에도 적용된다.
