사용자는 이 프로젝트의 UI를 다듬을 때 거의 매번 참고 이미지나 스크린샷을 함께 첨부하고("[Image] 여기를 이렇게 고쳐줘"), 한 번에 큰 변경을 요청하기보다 한 화면의 특정 요소 하나씩(폰트 크기, 색 하나, 배지 위치 등) 소규모로 여러 차례 반복 조정하는 방식을 선호한다.

**Why:** 브라우저 자동화가 연결되지 않는 환경([[feedback-ambiguous-visual-requests]] 참고)에서 사용자가 직접 눈으로 확인한 결과를 스크린샷으로 되돌려주는 것이 유일한 시각적 피드백 루프이기 때문으로 보인다.

**How to apply:** 이미지가 첨부된 요청은 그 이미지를 최우선 근거로 삼아 구체적으로 구현하고, 이미지 없이 애매한 형용사로만 표현된 요청은 먼저 확인 질문을 던진다. 큰 리디자인을 한 번에 몰아서 제안하기보다, 사용자가 요청한 범위로 좁혀 작게 작게 반영하는 편이 이 사용자의 작업 방식과 맞는다.

**추가 관찰(2026-09-22):** 이미지 없이도 `background: var(--bg);`, `box-shadow: 0 8px 32px rgba(20, 21, 26, 0.12);`, `margin top을 40px 정도` 처럼 CSS 속성/값을 그대로 채팅에 적어서 요청하는 경우가 많다 — 이런 요청은 "애매한 형용사"가 아니라 이미 구체적인 지시이므로 [[feedback-ambiguous-visual-requests]]의 확인 질문 대상이 아니라 바로 적용한다. 다만 그 값이 다른 CSS와 충돌하거나(예: body 배경색을 .container와 같게 만들면서 동시에 모서리를 둥글게 해달라는 요청처럼) 부작용이 있을 땐 적용은 하되 부작용을 짚어준다.

**추가 관찰(2026-09-23):** `.qr-actions .btn-secondary 에서 flex를 없애줘`, `.qr-actions .btn-secondary 자체를 삭제해줘`, `.btn-secondary:hover 기능 삭제해줘`처럼 정확한 CSS 선택자/속성명을 그대로 지칭하며 "없애줘/삭제해줘"라고만 짧게 요청하는 경우도 같은 원칙(이미지 첨부 요청과 동등하게 구체적)으로 이미지 없이 바로 실행한다. 확인 질문을 던지지 않았고 매번 의도한 대로였다. 다만 삭제로 인해 그 값에 의존하던 다른 규칙(예: 관련 주석, 다른 셀렉터가 공유하는 같은 속성)이 죽은 코드나 드리프트가 되지 않는지는 적용과 동시에 직접 정리해야 한다 — 사용자가 그 부분까지 언급하지 않기 때문. [[feedback-post-approval-redesign-expected]]도 참고 — 승인된 기존 스타일 결정이라도 예외 없이 되돌려달라는 지시를 그대로 따른다.
