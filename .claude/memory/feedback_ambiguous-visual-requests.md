애매하게 표현된 시각적 요청(예: "여기 가독성이 좋게 만들어줘", "더 크게")을 받으면, 무엇이 문제인지 스스로 추측해서 바로 CSS를 고치지 말고 AskUserQuestion으로 2~4개의 구체적인 해석 후보(예: "크기/간격 대비 부족" vs "색상 대비 부족" vs "아이콘 굵기 문제")를 제시해 확인부터 받는다.

**Why:** 이 프로젝트에서 `mcp__claude-in-chrome__*` 브라우저 자동화 도구가 세션 내내 한 번도 정상 연결되지 않아, 실시간으로 렌더링 결과를 직접 확인할 방법이 없다. 이 환경에서 추측성 CSS 수정을 반복했다가 사용자가 여러 번 정정해야 했던 전례가 있다(이 세션 압축 이전 구간). 반대로 "규리 → 가 함께 기도하고 있어요" 폰트 크기처럼 이미지가 함께 제공되고 요청이 명확한 경우엔 바로 수정해도 문제없었다.

**How to apply:** [[user-screenshot-driven-iteration]]과 함께 적용 — 사용자가 스크린샷/참고 이미지를 첨부했고 요청이 명확하면(예: "바코드를 스탬프로 바꿔줘", 참고 이미지 첨부) 바로 구현. 이미지 없이 형용사만으로 표현된 요청("가독성 좋게", "더 낫게")이면 반드시 먼저 후보를 제시해 확인받는다.

**⚠️ 2026-09-27 갱신 — "이미지가 첨부됐으니 명확한 요청"이라는 전제 자체가 항상 성립하지는 않는다.** 사용자가 두 장의 참고 이미지(수정 대상 UI 스크린샷 + "이렇게 만들어줘"라며 붙인 전혀 다른 도메인의 이미지, 예: 배달앱 요금 카드)를 첨부했는데, 두 이미지의 콘텐츠가 구조적으로 대응되지 않는 경우(대상 화면엔 숫자/가격이 없는데 참고 이미지는 "큰 숫자+취소선" 레이아웃인 식)가 있었다. 이땐 이미지가 있어도 "정확히 어느 요소를 어떻게 가져올지"가 여전히 불명확하므로, Chrome 자동화 연결 여부와 무관하게 AskUserQuestion으로 적용 범위(부분 스타일만 차용 vs 전체 구조 재구성 등) 후보를 먼저 제시해 확인받았고, 사용자가 후보 중 하나("전체를 카드 스타일로 재구성")를 바로 골라줘 왕복 없이 진행됐다. [[project-qr-sheet-flat-card-redesign]] 참고.

**⚠️ 2026-09-23 갱신 — 위 "Chrome 자동화가 세션 내내 한 번도 연결 안 됨" 전제가 더 이상 사실이 아니다.** 이번 세션에서는 `mcp__claude-in-chrome__*`(navigate/computer screenshot·click·zoom/read_console_messages)가 정상 연결되어 매 CSS 변경마다 직접 스크린샷으로 확인하며 작업했다. 즉 이 메모리의 "먼저 AskUserQuestion으로 후보 확인" 규칙은 **Chrome 자동화가 끊긴 상태에서만** 적용하고, 연결돼 있으면 애매한 요청이라도 먼저 시도해보고 스크린샷으로 직접 검증한 뒤 필요하면 조정하는 쪽이 더 빠르다(이번 세션에 여러 차례 이 방식으로 왕복 없이 바로 확인·수정했다).
다만 새로운 함정을 하나 발견했다: 대화 도중 tab 그룹이 끊기면(`tabId ... is not in Claude's tab group`) `tabs_context_mcp`로 새 탭을 새로 만들게 되는데, 이 새 탭이 이전 탭과 같은 브라우저 프로필의 캐시를 그대로 물고 있어 **일반 `navigate`만으로는 방금 수정한 CSS가 반영되지 않고 옛 화면이 그대로 보일 수 있다.** 실제로 이 때문에 사용자가 "왜 롤백된 것 같지?"라고 오해한 적이 있다 — 탭이 새로 생성된 직후나 원인 불명의 "예전 모습이 보인다"는 보고를 받으면, 먼저 `computer` 액션 `key: "cmd+shift+r"`(강력 새로고침)로 캐시를 무시하고 다시 확인할 것. 파일 자체는 항상 최신인지 `curl`/`grep`으로 먼저 확인해 코드 문제와 캐시 문제를 구분한다.

**⚠️ 2026-09-30 갱신 — Chrome이 연결돼 있어도 "애니메이션/모션 효과"류 요청은 여전히 오역 위험이 크다.** "말풍선 텍스트가 오른쪽에서 왼쪽으로 흘러가는 효과 추가해줘"라는 텍스트만 있는 요청을 받고 "고정된 텍스트 위로 빛 그라디언트가 지나가는 하이라이트 스윕"으로 구현했다(스크린샷으로 애니메이션 동작 자체는 검증 완료). 그런데 사용자는 실제로는 "텍스트 자체가 고정폭 창 안에서 잘리며 흘러가는 진짜 마퀴(ticker)"를 원했고, 참고 이미지(글자가 창 가장자리에서 잘린 프로모션 배지)를 보여주며 "내 말은 이런식으로!"라고 정정했다. 두 구현 다 "오른쪽→왼쪽으로 흐르는 것처럼 보인다"는 점에서는 동일해서, Chrome 스크린샷으로 "의도대로 작동하는지"만 확인해서는 이 오역을 잡을 수 없었다 — 정적 스크린샷/짧은 동작 확인으로는 "애니메이션이 재생된다"는 것만 검증되지 "어떤 종류의 모션인지 사용자가 의도한 것과 같은지"는 검증이 안 된다. **How to apply 보강:** 모션/애니메이션 효과를 텍스트 설명만으로 요청받으면(참고 이미지·GIF 없이), 구현 전에 "무엇이 움직이는가"(콘텐츠 자체 이동 vs 오버레이 이펙트)를 먼저 명확히 할 것 — 애매하면 빠르게 시도해보고 스크린샷으로 "그럴듯해 보이는지"만 확인하고 넘어가지 말고, 짧게 재확인 질문을 던지는 게 더 안전하다.
